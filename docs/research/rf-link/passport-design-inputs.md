# AI Passport 版本：设计输入与待确认事项

> 2026-10-31更新：用户已在Web音频试听后选择纯BLE手咪和App网络身份，见[ADR0003](../../adr/0003-rf-link-ble-handmic.md)及[当前协议草案](../../spec/rf-link-handmic/README.md)。本文保留此前独立联网方向的分析，不应将下文A方案/独立设备证书要求套给纯配件首版。

本文件是调研后的设计讨论材料；用户已确认独立联网电台方向，其他分工与首版范围仍在讨论，并非完整实现计划。现有iOS事实见[功能流程](features-and-flows.md)与[协议/身份](protocols-and-identity.md)。功能删减、首版范围和硬件按键交互须由用户确认后再进入规格与ADR。

## 1. 已确认原则

1. 开发AI Passport版RF Link，参考当前iOS App的真实功能与公开协议。
2. 正常使用下每个登记实例使用独立证书/密钥；不复用手机自身RF Link证书给多个终端。
3. 不对非自有硬件做eFuse写入、永久锁机等不可逆修改；保持可清除/解绑/恢复。
4. 当前不追求抵抗用户主动伪造/克隆，重点是正常用户唯一配对和明确授权。
5. Ed25519业务私钥不放Passport；BLE远程签名已经验证，手机或电脑Web可作为签名端。正式端的私钥存储策略仍需另定，实验公开明文种子不自动扩展为生产策略。
6. 用户已授权BLE签名验证迭代写入且无需备份；这不自动授权未来完整RF Link产品的烧录、证书申请、生产连接、发布或部署。
7. 所有固件构建走本仓库Docker/`./tools/dev`，本地组件与独立应用不复制上游UI，不安装主机ESP-IDF。
8. 用户已确认采用独立联网方向：Passport自行通过Wi-Fi运行语音链路，签名由外部端协助；首配选择App BLE还是Web仍待决定。

## 2. 硬件与已验证能力

| 项目 | 当前事实 | 对设计的影响 |
| --- | --- | --- |
| 主控 | ESP32-C3，8MB Flash，无PSRAM；实物rev v1.1 | 不能按手机内存/CPU规模复制全部服务 |
| 网络 | 2.4GHz Wi-Fi、BLE | Wi-Fi业务与BLE代签可分工；音频负载下共存未测 |
| 屏幕 | 240×320彩屏 | 需重新设计可读状态与列表，不复制iOS滚动大首页/地图 |
| 输入 | 上/下/OK三键共用ADC；独立硬件电源键 | 没有独立PTT键/触屏键盘；不能默认可靠组合键，也不能直接把电源键当软件按键 |
| 音频 | ES8311、麦克风/扬声器、I2S全双工；BSP提供read/write/set_format | 有音频I/O基础，不代表8kHz codec实时收发、噪声/增益/切换已验收 |
| 定位 | 硬件清单没有GNSS | 必须明确手机供应/手动配置/无位置策略及年龄 |
| 电源 | 500mAh、电量计、背光与睡眠基础 | 息屏是否仍守听、重连功耗、低电量策略须测量和设计 |
| 存储 | 当前factory单应用分区，无OTA双槽 | 不承诺OTA；NVS分命名空间保存配置，不能擦其他应用数据 |
| BLE实验 | 设备确认单公钥绑定、12次最终成功，连续10/10约0.7s、异常拒绝/恢复 | 证明基础传输可用，不是生产证书、SAS或完整电台证明 |
| 实验内存 | BLE+LVGL空闲堆约117KB，main栈已扩大12KB | 新增Wi-Fi/TLS/Opus/CBOR/CRL时须重新测峰值，不能用8MB Flash推断RAM足够 |

硬件源：本仓库`vendor/ai-passport/docs/hardware-design/specifications.zh_CN.md`及`components/bsp/include/bsp_pins.h`、`bsp_audio.h`；后两者位于vendor目录下。原型证据见[BLE验收记录](../../development/ble-signer-lab-validation-2026-10-31.md)。

Passport不是VHF/UHF收发机；BEACON中的频率/天线/电台资料描述用户填写的外部无线电环境，不能由本机操作自动调节不存在的射频硬件。

## 3. 两种可讨论的产品分工

| 候选 | Passport承担 | 手机/Web承担 | 取舍 |
| --- | --- | --- | --- |
| A：独立联网电台＋远程签名 | Wi-Fi、MQTT、RAW、codec、麦克风/扬声器、PTT及小屏运行状态；APRS/QSO范围待定 | 独立设备密钥/证书管理，配网/配置，签名及可能的定位/目录辅助 | 接近独立终端；音频不走BLE，但C3实时性和资源压力最大，需要优先验证 |
| B：手机网络与音频网关＋配套终端 | 按键/显示、音频采集播放、BLE控制/音频传输 | MQTT/APRS、codec、认证、业务状态和存储 | 降低部分ESP32网络/业务负担；更依赖手机，BLE持续音频吞吐、时延和后台均未验证，原代签实验不能证明它可用 |

**用户已确认A：独立联网电台＋远程签名。** Passport承担Wi-Fi实时语音链路，不以手机作为音频/网络网关。初始化配置及长期签名端选择仍待讨论；实时codec/内存等工程风险仍须验证，不能提前承诺全量移植。

无论A/B，都不能把“手机握有一张证书”自动当作Passport的证书；手机应为每个登记实例管理不同私钥和证书，并保留自身身份隔离。

## 4. 正式BLE能力还缺什么

现有实验的消息是自造UTF-8挑战文本，最大192字节，公钥绑定、20字节JSON分片、10秒超时；没有正式业务字段、证书生命周期、SMP链路保护或多业务RPC。生产设计应先明确以下合同，再扩实现：

| 能力 | 需要确定的字段/规则 |
| --- | --- |
| 登记实例 | 稳定instanceID、显示名、公钥/证书身份、签名端身份；普通解绑是否保留登记身份 |
| 证书申请 | 哪一端提交材料、生成实例密钥、取challenge、存待审核状态；同呼号多证书需CA政策确认 |
| 认证材料 | Root/Intermediate/User的JSON与CBOR、指纹、UID、有效期、授权截止，版本与总长度限制 |
| 代签请求 | 协议版本、requestID、业务用途、目标服务器、身份ID、TBS原始bytes或可重建的结构化字段、期限、取消/错误码 |
| 请求校验 | 手机按业务类型授权和重建/核对TBS，避免只暴露无限制任意字节签名；设备校验返回结果与当前请求 |
| 连接/换服 | 每次CONNECT生成新proof，不重复使用过期凭证；切服取消旧签名，旧响应不能接管新会话 |
| 并发与传输 | 配网/目录/位置/签名互不饿死，长度、分片、流控、重试/幂等、断线作废；通知与读状态使用独立特征 |
| 时间与状态 | 时钟来源、校时失败、CRL/证书授权截止与时间盐、手机后台/断连如何提示 |
| 迁移与恢复 | 换手机、撤销绑定、清缓存、重刷固件、证书到期/吊销；不能把本机删除当远端吊销 |

iOS的`DirectVoiceIdentityProviding`已有签名抽象，但当前Keychain私钥账户只按规范化呼号区分，申请存储为全局单个待处理记录（固定`Enrollment/enrollment.json`），两者均没有设备实例维度；不存在Passport BLE服务，不能只加一层BLE转发就宣称完成多设备身份管理。证据：`DirectVoiceIdentity.swift:397,451`、`EnrollmentStorage.swift:24`。

## 5. 功能迁移讨论矩阵

以下以候选A为讨论基线，是归属建议，不是首版删减决定。若选择B，codec、网络业务、记录与信任验证须重新分配，不能把本表的设备侧工作自动套给B。

| iOS能力 | Passport上的合理呈现候选 | 手机/Web辅助候选 | 尚待决定 |
| --- | --- | --- | --- |
| 实名材料/证书申请 | 显示登记、审核、可用、失效状态 | 图片、表单、领取及独立实例私钥 | 新设备如何申请与领证 |
| 配网/服务器配置 | 选已配置Wi-Fi/服务器、显示连接原因 | 输入密码、手动服务器字段、收藏/目录同步 | 首配入口、手机不在时可选范围 |
| 守听/PTT | 主界面、呼号/服务器、占线、音量、持续按键讲话 | 不承接A方案的实时音频 | 三键PTT/导航冲突、默认声音与锁键 |
| codec | 接收兼容Opus与RADPCM；发送模式单独选择 | 仅提供配置 | 首版是否两种均发；必须先测CPU/RAM |
| APRS动态/目录 | 小列表/文字详情；不默认移植地图瓦片 | 大地图、长目录、搜索与配置 | 首版展示与接收/验签归属 |
| ONLINE/CQ/BEACON | 简单可解释的显式操作与授权状态 | 位置/频率/设备资料录入 | 默认开关、缺位置行为、SSID规则 |
| QSO | 摘要、交换状态、有限列表与保存故障 | 搜索/编辑/长期保存/后续导出 | 是否要求离手机独立保存完整记录 |
| TELE/RIG | 共享状态与当前资料提示 | 填写长文本/网格/频率 | 独立共享授权及默认值 |
| 推送 | 本地提示仅在已定义条件下 | APNs属于手机业务 | Passport是否需要任何远端提示 |
| 身份删除/解绑 | 本机明确确认、只清自身数据 | 证书撤销/换设备/换手机流程 | 解绑与注销身份是否独立 |
| 主题/设置 | 中文可读字体、电量/网络/签名端状态、音量与发射模式 | 长文本/隐私/高级配置 | 设置层级和常用快捷动作 |

## 6. 设计必须覆盖的异常状态

| 场景 | 不应省略的业务区别 |
| --- | --- |
| 已配网但未绑定签名端 | 不是Wi-Fi故障；无法取得新的认证签名 |
| BLE在线但无正式证书 | 配对成功不等于领证成功；不得拿测试身份上生产 |
| Wi-Fi断线、签名端在线 | 新连接需要新的SAS签名；有界退避，PTT不得阻塞等待 |
| Wi-Fi在线、BLE断线 | 是否允许现有会话继续至授权截止需决定；不能承诺一定立即停，也不能承诺永远可通话 |
| 证书/CRL失效或暂不可验证 | 与服务器不通不同；新发射/重连需遵守明确定义的授权门控 |
| 切服时旧签名返回 | 通过会话代次/请求身份隔离，不把旧proof发到新目标 |
| 配置/目录/位置陈旧 | 可以显示缓存，但不能把缓存时间等同当前在线或当前精确位置 |
| PTT中打开菜单/掉网/低电量/系统睡眠 | 明确停止发射、尾包与提示，不能留下“按住”状态 |
| QSO发送成功但保存失败 | 保留可重试结果，不能重复网络发送伪造新的交换 |
| 手机换机/浏览器清数据 | 凭据、绑定、证书分别恢复或重新登记，不能静默换身份 |

## 7. 首先需要验证的工程问题

这只是风险消除顺序，不是已批准的实施排期。

1. **跨实现协议向量**：从当前Swift测试提取公开虚构身份的CBOR/User CERT/SAS/APRS/RAW/CRC/QSO/TELE/RIG向量，建立C侧逐字节兼容验证；不得复制真实Keychain或生产材料。
2. **真实身份链路**：确认CA同呼号多实例政策；以获准的测试身份完成独立设备证书申请/导入与SAS CONNECT、CRL过期/回滚/吊销拒绝；现有公开实验种子不能代替正式证书。
3. **资源与音频**：C3编译并测8kHz Opus/RADPCM每帧时间、栈/峰值堆、I2S读写与音量，持续收发、丢包/抢断；先证明实时路径再堆UI。
4. **Wi-Fi/BLE共存**：在MQTT/TLS/音频持续运行时请求代签/位置/配置，量化断连、抖动、缓冲积压和重连耗时。
5. **信任材料预算**：iOS HTTP/CRL上限256KiB、缓存与JSON对象不能按原上限整体照搬到当前空闲堆约117KB的设备；需决定流式/分块Flash缓存、受控上限或手机验证委托等策略，后者会改变信任边界，不能暗中削弱验签。
6. **三键与电源**：新中文小屏页面、按下/释放PTT、菜单退出、锁键、息屏守听、续航及低电量安全停止；既有练耳播放/按键结果不能替代这些验收。

BSP默认16kHz，线路8kHz；要明确何处改采样格式/转换，切格式前停PCM读写并串行化BSP操作。不要把iOS AVAudioEngine重采样、系统回声处理及后台行为想当然视为ESP32现成能力。

## 8. 下一轮讨论的关键问题

按影响程度逐项确认，不需要一次回答所有细节：

1. 已确认A：Passport独立Wi-Fi收发语音；接下来选择App BLE或Web承担初始化和后续签名服务。
2. 首版必须包含哪些：基础语音、CQ/上线、信标/附近、QSO、TELE/RIG、完整网络动态？
3. 手机不在或BLE断开时，已认证的会话允许怎样继续，授权截止如何得到/刷新？
4. 手机与Web分别是开发工具、可替代签名端还是长期支持的正式产品入口？
5. 独立设备证书申请与换签名端的服务端政策/所有权恢复流程如何安排？
6. 三键PTT、导航、音量、息屏/锁键的期望操作是什么？

确认方向后再写`docs/spec/`下的RF Link产品规格与技术边界、中文交互方案，并将真正确认的重大架构决定记入ADR；之后才排实现计划及产品固件开发。
