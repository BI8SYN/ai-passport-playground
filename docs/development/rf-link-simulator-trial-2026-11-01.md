# RF Link Mac/Web模拟器与首次iOS采样

用户为定位实体Passport断续，授权制作Mac模拟BLE外设、Web还原Passport的诊断工具，不查看外部iOS源码、不刷写实体固件。实现见[工具说明](../../tools/handmic-simulator/README.md)。

实际验证：C后端Docker构建通过、8项黑盒测试通过；Web/原有工具合计32项测试通过；AudioWorklet短片段/清空/麦克风帧测试通过；Swift桥编译、plist与严格签名验证通过（显式macOS13 deployment target，修复默认minOS28导致当前系统无法启动）。真实Web界面由独立Chrome配置截图检查，实际CoreBluetooth poweredOn及服务广播/手机3项订阅/max244、HELLO和语音收包已发生。实体串口未打开、固件和绑定未改。

## 共享接收核心的独立复现

进一步用同一份已编译核心做A/B输入，不改产品源码、不重启当前BLE模拟器：每10ms送一帧，共30帧；每5帧的序号跳过1帧，两组PCM和序号完全一致。A组仅首包带断续标记，B组首包及每5包带断续标记（20%，接近采样中的19.1%，但不假定真实标记就是等间隔）。

结果：两组核心都接受30/30帧、无late/overflow。A组在输入结束前播放20个非零PCM帧，B组播放0个；B组欠载仍为0，因为一直未到消费时刻，未进入欠载计数。原因由源码直接解释：hm_core_audio_accept对每个断续标记都设置consume_ms=now+60；标记每50ms来一次，起播期限不断后移，形成播放饥饿。

复现脚本/日志在本地`artifacts/handmic-simulator/repro_discontinuity.py`及`discontinuity-repro.log`，输入为合成常值PCM，不是用户录音。该实验确认了接收核心存在可复现缺陷，并说明不能只凭欠载计数排除播放停滞；但用户导出只有汇总，尚不能证明实际272个标记的逐帧间隔或解释全部836个拒收。

建议最小修正方向：新流首次起播保留60ms预缓冲；流内断续推进序号/丢弃旧槽，不无限重启60ms等待，补密集断续/信用/时间边界回归并同步协议文字。该方向尚未实施、编译或烧录，须在用户要求修复后执行；iOS发送跳帧/背压仍另需排查。
